5. Implement Execution Planner

Execution Planner owns:

* surface
* model
* reasoning level
* tools
* plugins
* skills
* execution notes

Consolidate the useful execution-routing responsibilities previously spread across Project Status / Prompt Coach / model and surface recommendations.

Prefer concise output.

Support this distinction when meaningful:

Good enough
Lowest-cost configuration expected to complete the task reliably at the requested quality.

Best worth using
Higher configuration only when the expected improvement meaningfully justifies additional usage.

Do not mechanically recommend the strongest model or highest reasoning.

When a higher setting is unlikely to materially help, say so.

Usage estimation itself remains Usage Gauge’s responsibility.

Dynamic capability routing:
* Base recommendations on the models, reasoning levels, surfaces, tools, plugins, and skills actually available in the current environment when that information is exposed.
* Do not maintain a hardcoded catalog of model names or reasoning levels. Newly available capabilities should become eligible automatically without requiring this skill to be updated.
* Availability and suitability are separate: discover available candidates, then recommend the configuration that fits the task.
* Never invent unsupported model/reasoning/surface combinations. If current availability cannot be determined reliably, say so rather than relying on a stale catalog.
* Do not trigger expensive research merely to make a routine recommendation. Verify current capability details only when they materially matter.

8. Refine Prompt Coach

Prompt Coach remains separate from Prompt Cleanup.

Prompt Cleanup:

North star: “Rewrite what I just said so I said it better.”

Its intended use is a large, messy, stream-of-thought prompt that needs to become a clearer, tighter, better-organized version of the same request before execution.

* produces faithful, optimized replacement text;
* preserves every distinct intent, requirement, constraint, preference, example, uncertainty, named entity, path, URL, and meaningful nuance;
* removes genuine redundancy and filler without silently dropping ideas;
* improves wording, organization, and execution clarity without introducing new requirements or redesigning the task;
* can optimize unnecessary context/tool instructions when doing so does not change intent;
* does not add project-management machinery, execution planning, critique, scoring, or unrelated recommendations;
* does not execute the rewritten request unless separately asked;
* by default, returns only the complete cleaned replacement prompt, preferably as raw text in one copyable code block, with no preamble or postscript unless clarification is genuinely required.

A subsequent “approve,” “use it,” “run that,” or equivalent may be treated as authorization to execute the cleaned version.

Prompt Coach:

* teaches/recommends improvements;
* retains useful coaching behavior;
* retains the approved X/Y/Z interaction where appropriate;
* for substantial prompts, may point out missing or unclear success criteria when that observation would materially improve the result, without forcing a formal template.

Remove duplicated ownership of execution routing now assigned to Execution Planner.

Forecast calibration

Representative expectations:

* meaningful multi-file analysis/verification → 🟠 Heavy
* substantial multi-file implementation/research → 🔴 Intense
* unusually broad multimodal/research/implementation scope → 🚨 Extreme

These are behavioral expectations, not rigid formulas.

Output discipline

Default explicit invocation should remain tiny, e.g.:

Optionally one supported saving suggestion.

Do not turn routine activation into a resource audit.

Preserve:

* forecast vs measurement distinction;
* no invented context percentages;
* no fake Plus allowance calculations;
* bounded before/after measurement;
* telemetry unavailable ≠ zero;
* no unsupported task-level attribution.

Implementation discipline

Prefer editing existing artifacts over creating redundant ones.

Do not revisit accepted architectural decisions unless implementation reveals a concrete contradiction.

If a minor implementation choice is reversible and consistent with this specification, choose the simplest reasonable option and continue.

If a choice would materially change the accepted architecture, stop and surface it rather than silently redesigning the project.

Keep Git commits coherent and suggest/use checkpoint commits at meaningful milestones.

Do not push broken intermediate states merely for backup; push coherent checkpoints.

Minimize unnecessary repository scans, repeated context loading, and validation loops.

At completion, report:

* files changed/created;
* behavioral changes;
* validation performed and results;
* unresolved issues;
* Git commit(s)/push state;
* recommended next action.
